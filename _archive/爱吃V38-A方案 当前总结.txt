3. 重要决策记录

算法决策（已固化到 .claude/skills/menu-scoring-philosophy/SKILL.md）

Rule 0 · 算法必须公平 —— 同样性质的信号在不同用户身上产生同样强度的偏好。固定 origin 加分表（粤 0.15 / 川 0.10）已弃用。

Rule 1 · 家乡权重显著大于其他 —— hometownMatches() match 给 +0.60；非家乡其他中餐 +0.04。设了家乡的用户家乡菜 net = +0.60，差距 0.56。没设家乡的用户走平等模式（四大中餐 +0.08 一律）。

Rule 2 · 使用数据走累积计数 + 幂次方曲线 ——
- 存储：user_preference_scores 表里所有 pref_* 列改为累积计数（每次 keep +1，每次 swap −0.5），cap ±25
- 评分：usagePower(n) = sign(n) × |n|^1.5 × 0.05
- 标定：5 次川菜 → +0.56 ≈ 家乡 +0.60 持平；10 次 → 完全超过；20 次 → 主导。
- 替换了旧的 EMA（0.85 衰减 + 0.667 饱和模型）

Rule 3 · 首次推荐特别重要 —— isNewUserSession() 为 true 时：profile-match 每命中 +0.15、social-popularity (health_score / times_kept_in_menu) +0.10/+0.08。返回用户走 prefScores 累积 + 幂次方。

Rule 4 · 高端中餐 chef framing —— 季节性 +0.08（seasonal_tag 命中当前月）；盖饭/便当/炒饭/烩饭 −0.15；粥/稀饭 lunch+dinner 池前 strip；同日 cook_method 重复 −0.30。

Rule 4.5 · 西餐高端 HK premium —— origin='western' 内部二级 bias：意/法/西班牙/地中海/普罗旺斯/摩洛哥/土耳其 等 +0.12；三明治/汉堡/玉米饼/牧羊人派 等 −0.08。

Rule 4.6 · 试用期满锁 Home 菜单 —— !isPro && !isWithinTrial() → <TrialExpiredCard/> 替代菜单。试用期 7 天，从首次登录起算。

Rule 5 · 家乡选项 = 地域大区（2026-05-17 改版）—— 旧八大菜系覆盖率仅 ≈ 60% 大陆人口。新选项 9 chip：华南/华东/华北/东北/西北/西南/华中/港澳台 + 都行 / 没偏好。华中 → northern（河南占人口主导）。Legacy 八大菜系 id 保留兼容。

Rule 5.5 · 早餐 pool 是 DB-shape-dependent —— pickBreakfastCombo pool-aware rotation：当前 combo 在 pool 中 0 命中时自动 rotate 到 universal '*' combo。修了 sichuan × breakfast = 0 的 DB gap（已补 7 道川菜早餐 + 3 道升级 meal_type='all'）。

Rule 6.5 · 拒绝 scoring_rules 配置表（2026-05-18）—— YAGNI + 双源真相风险 + LLM agent self-knowledge 应读 skill 文件不读 DB + 配置变更走 SQL 比 git 慢 + 提案自带的 USE_DB_SCORING_RULES=false escape hatch 证明这是 dead infrastructure。重启条件：实际 A/B 实验调度或 Composer/Critic 真的需要结构化访问。

Rule 6 · Cache invalidation 纪律 —— 改算法必须 bump ALGO_VERSION。v25 → v37 完整历史在 skill。

Rule 7 · Disagree on the record —— 收到产品方提案时先说反对意见再实现；决议结果固化到 skill 留 paper trail。Rule 6.5 就是这条流程的产物。

5. 风险与注意事项

高风险

1. menu_evals RLS anon-insert 风险 —— WITH CHECK (true) 意味着匿名用户能伪造 user_id 注入垃圾数据。当前是 user_feedback / user_preference_scores 的同款模式（CLAUDE.md anonymous-auth 固有妥协）。v1 接受，v2 上线前应改为 service_role-only INSERT 走 edge function。
2. vector(768) 维度锁死 = Gemini text-embedding-004 —— 一旦 backfill 开始就不能换 embedding 模型（Voyage / OpenAI 维度不同），换的话要重做 020 类型迁移。
3. DB 720 行远不足以撑 7 天 × 4 人家庭一年的菜单不重样 —— recency_decay < 7d -0.60 / < 14d -0.30 / < 30d -0.15 已经在防重复，但池子小 + 家乡过滤后实际可用菜更少。中长期需扩到 2000+ 道。
4. scoring_rules 决议是单向的 —— Rule 6.5 已写"重启条件"。如果未来真要做 A/B test，新表名建议是 experiment_assignments 而不是 scoring_rules，更贴近真实需求。

中风险

5. CLAUDE.md / SKILL.md / 代码 三处都描述算法 —— SKILL.md 是最新的真相源。下次大改算法时同步三处避免 drift。
6. menu_evals.composer_run_id 是 uuid 但无 FK —— Critic 行 link 回 Composer 行靠 app 层维护。如果 app 写错 id，孤立 row 不会自动报错。建 partial index 已经能让查询效率 OK，但数据完整性靠 app 层。
7. user_preference_scores 累积计数 cap ±25 —— 一个 spam 账号在 25 步内能把 prefScores 推到 cap，cap 之后无效但仍能阻止其他用户的影响进入。这是 power curve 的 sanity bound，不是 abuse 防御。abuse 防御要在 swapFeedback 写入层做（per-user rate limit）。

低风险（仅记录）

8. uuid-ossp / pgcrypto 已装在 extensions schema —— vector 跟它们一致。未来如果要改 search_path，记得 extensions 必须保留。
9. apply-XXX.ts 模式跟 Supabase CLI 共存 —— 我们走 pg.Client 直接 INSERT tracker，CLI 也能识别（看 version 列）。但 CLI 自己跑会填 statements 列，我们的不填。未来切回 CLI 模式时，已有的 018 / 020 行可能要手动补 statements，或者放弃这两条让 CLI 重跑（DB 已有列会触发 IF NOT EXISTS 跳过，安全）。
10. docs/HANDOFF.md 提到的 3 个"repo 有 / tracker 没"重复编号文件（004_stripe / 006_household_drop_auth_fk / 008_user_favorite_dishes）—— 它们的内容已通过 node + pg.Client 应用过，DB 状态正确，仅 tracker 没收录。不影响 018 / 020 / 后续工作。
