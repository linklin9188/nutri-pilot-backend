# 爱吃护城河战略 — 四层架构 (2026-05-30 老板拍板)

> 起因: 老板用 Salesforce 四层核心架构 (Data Cloud → Customer 360 →
> Agentforce → Slack) 反问 "爱吃该怎么优化才有持续竞争力"。
> 这份文档把那次分析定稿, 作为**每个功能决策的取舍标尺**。

---

## 0. 核心论点 (一句话)

**在 AI 时代, UI 和"调用 AI"都是零护城河的 (人人能做)。真正难替代的是中间
那层沉淀的复杂业务规则 + 双边数据。**

Salesforce 的图点破: 很多人以为 SaaS 价值是页面, 其实真正难替代的是
Customer 360 那层沉淀十几年的审批流 / 触发器 / 定制逻辑。爱吃同理。

---

## 1. 爱吃映射到四层

| 层 | Salesforce | 爱吃现状 | 护城河强度 |
|---|---|---|---|
| **顶: 协作 / 通知** | Slack | 雇主↔菲佣绑定、共用做饭流、反馈卡、社区 | 中 (双边是结构优势) |
| **AI Agent** | Agentforce | gemini-proxy / chat / 意图解析 | **零** (租 Google 模型, 人人能调) |
| **业务系统 (真护城河)** | Customer 360 | 算法 v72 + 编码的中餐家庭规则 + 雇主意图→菲佣执行闭环 | **该押这层** |
| **底: 数据真相源** | Data Cloud | 菜库 + 偏好 + household 图谱 | 中 (但现在是碎的) |

---

## 2. 我们真正的护城河只能在"业务系统层"

**不能是这些 (零护城河)**:
- 漂亮 UI — AI 几分钟生成一个比我们好看的菜单 app
- "AI 推荐吃什么" — 竞品调一下 GPT 就有
- 菜品数据本身 — 能爬、能买、能让 LLM 生成

**必须是这个** (对应 Salesforce 那"十几年审批流"):

> **"在港大陆家庭 ↔ 菲佣"双边场景里, 每个家庭沉淀的偏好规则 + 雇主想吃到
> 菲佣真做出来的完整业务闭环 + 72 版算法里编码的中餐家庭真实规则。**

为什么 LLM 包一层 UI 复制不了:
1. **算法 v40→v72 每次 bump = 一条真测喂出来的永久业务规则** (早餐不能全是
   粥、晚餐要有主食、备孕+增肌家庭分槽…)。这个 changelog 字面上就是护城河
   账本, 竞品没有这两周的真测反馈。
2. **双边数据飞轮**: 雇主 chat/换菜/收藏 → 偏好; 菲佣做完/不会做 → 执行真相;
   雇主打分 → 菲佣动力。每个 household 越用越厚的双向数据, 新玩家从零拿不到。

---

## 3. 优化优先级 — "挪重心"

### 少投 (在 Agentforce / UI 层瞎卷)
- 别花精力让 AI "更聪明" — 那是租 Google 能力, 护城河为零
- 别堆更多花哨 AI 功能
- 别在 UI 美化上过度投入 (够用即可)

### 多投 (往中间两层沉淀)

**① 底层数据先统一 (Data Cloud)**
现在数据是碎的 — Smell 1 (两套菜单算法 useRecommendDishes vs
useWeeklyMenu)、Smell 2 (画像存 localStorage + DB 两处不同步)。这不是
"技术债清理", 是**护城河地基在漏**。
→ 所有信号必须挂到 household 这个唯一实体上, 落一个地方。

**② 业务规则层"可累积 + 锁定" (Customer 360)**
- 每条真测规则永久编码 (ALGO_VERSION changelog 就是规则账本, 继续维护)
- 雇主用得越久 → 沉淀偏好规则越多 → 换走成本越高 = 留存真来源
- 双边工作流 (做饭流 / 翻译 / 反馈闭环) 持续做深 — 这是竞品复制不了的部分,
  因为需要"两个角色 + 累积的 household 状态"

**③ 双边协作做深 (Slack 层)**
雇主 + 菲佣两个人天天在 app 里协作 = 结构性粘性 (Salesforce 买 Slack 就是
赌多人粘性)。
→ 做饭操作权互斥锁、做饭实时状态、推送通知 — 都是加深这层。

## 4. 决策对照表 (每个功能拿这个过一遍)

| 这个功能在建哪层? | 判断 | 动作 |
|---|---|---|
| UI 美化 / 新页面样式 | 顶层, 零护城河 | 够用即可, 不过度投入 |
| 接更强的 LLM / 更多 AI 功能 | Agentforce, 零护城河 | 只在性价比/省钱角度做, 不当护城河 |
| 算法规则 / 双边工作流 / 偏好沉淀 | **Customer 360, 真护城河** | **优先投, 持续做深** |
| 数据统一 / household 图谱 / 飞轮 | **Data Cloud, 地基** | **优先修, 别让它漏** |

**一句话过滤器**: "竞品调一下 GPT + 包个 UI 能不能一周追平? 能 → 别当护城河
投; 不能 (需要累积数据/双边磨合/真测规则) → 重点投。"

---

## 5. 最大风险 (必须正视)

**护城河现在还很浅** — 算法年轻、household 数据薄、用户少。Salesforce 是
十几年沉淀, 我们是两周。

**战略命令**: 现在就把飞轮转起来 + 保护它。最怕停在 UI/AI 功能层, 被更有钱的
玩家 (或美团 / 大众点评直接加个"AI 一周菜单") 一步跨过去 — 因为价值若停在那
层, 他们一天追平。

**唯一能让美团追不上的**: 等有 1000 个家庭, 每家沉淀半年的"雇主偏好 + 菲佣
执行 + 双边磨合"数据 — 那时换 app = 丢掉半年磨出的默契, 这个迁移成本才是真
护城河。
