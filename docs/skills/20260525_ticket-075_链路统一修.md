# TICKET-075 P0 — 全链路 6 断点统一修 (链路统一)

## 问题

老板真测 #18 完整链路: 雇主在 /weekly 生成菜单 → /verify 看采购清单
→ 菲佣 HelperPrep 看雇主已勾的"我家有" → HelperCook 做菜.

6 个断点把链路打散:

1. /verify 没"确认采购通知菲佣"按钮 — 雇主勾完无 commit 节点, 菲佣不知何时该看
2. 雇主"我家有"勾选只 LS 不 DB — 切设备 / 清缓存自己也丢
3. HelperPrep + HelperCook 读 `localStorage.generatedMenu` — 雇主菜单写在
   雇主设备, 菲佣自己设备 LS 是空的, 直接显空态
4. /verify 和 HelperPrep 食材聚合字段对不齐 — 哪怕 LS 共享了, 名字不同也不命中
5. swapDish 改了 DB 没改 LS.generatedMenu — 雇主换菜后菲佣看的还是老菜
6. 拍冰箱选完没"加收藏"分流 — 用户只能"全加到今天菜单"或放弃

真因: `localStorage.generatedMenu` + `home_inventory_<userId>_<date>` 这两个
LS 键被 4 个页面 (Home / WeeklyMenu / VerifyIngredients / HelperPrep /
HelperCook) 当主存使, 但 userId 是设备本地的, 雇主菲佣两套账号物理隔离,
跨账号 / 跨设备共享数据需求一旦出现就必断.

## 方法

数据迁移: LS 主存 → DB 主存 + LS 副 cache.

1. **新建 `home_inventory` 表** (migration 090) — `(household_id, ingredient_name,
   for_date)` 三元组 UNIQUE, FK→households 让雇主菲佣共享一行真相. RLS
   anon-first FOR ALL `USING (true)` 跟 Smell 3 修复后口径一致 (custom auth
   不能用 auth.uid()).

2. **新建 `src/lib/homeInventory.ts`** CRUD — `loadHomeInventory(hid, date)` /
   `setIngredientAvailable(hid, name, bool, by, date)` /
   `commitInventoryFromLs(hid, lsMap, by, date)` / `inventoryToMap(items)`.

3. **新建 `src/lib/helperEmployerMenu.ts`** — 抽 HelperHome 三步绑定查询
   (helper_id → household → employer → user_weekly_menus → dishes) 成可复用
   lib. HelperPrep + HelperCook + 未来其它菲佣页 共用一份逻辑.

4. **VerifyIngredients (雇主)** — mount 拉 householdId + DB load inventory,
   toggle 双写 LS+DB, 新加"确认采购通知菲佣"橙渐变按钮 (commit 全部 haveIt
   到 DB, 进 "已通知 X 项" done 状态). 兼容老数据: DB 空但 LS 有 → 一次性
   迁移 + sentinel 防重跑.

5. **HelperPrep (菲佣)** — 删 `localStorage.generatedMenu` 路径, 改读
   `loadEmployerTodayMenu(helperUid)` 拿雇主当日全部 dish. inventory 同样
   DB 主 + LS 副, toggle 双写 `markedBy='helper'`.

6. **HelperCook (菲佣)** — 同上改读 `loadEmployerTodayMenu`. 保留
   `?dish_id=X` 单菜路径不动 (那个不依赖菜单列表).

7. **useWeeklyMenu swapDish** — DB upsert 完后同步 `localStorage.generatedMenu`
   (只写 today 那天) + dispatch `nutri-weekly-menu-changed` event. ALGO_VERSION
   不 bump (零算法变化).

8. **Home 拍冰箱**双 CTA 并排 — "+ 加进收藏 (N)" (副, 灰底橙边) ｜ "看菜单 (N)"
   (主, 橙底白字). 收藏走 `addFavorite({...source_tag:'fridge_scan'})`,
   不跳页让用户继续逛.

## 标准

今后任何"雇主-菲佣 / 跨账号 / 跨设备共享"数据必须:

1. **DB 是 source of truth**, LS 只是副 cache (fast read + 离线兜底). 严禁
   出现"只在 LS 的状态" — 哪怕 PoC 阶段也要从一开始建表.
2. **抽 lib 防各页重复实现**: helper 多页用同一份雇主菜单查询走
   `loadEmployerTodayMenu`, inventory CRUD 走 `homeInventory.ts`. 不让
   HelperPrep / HelperCook / HelperHome 各写一份三步绑定.
3. **食材名/键名必须统一聚合后值** (aggregateIngredients 的 nameZh, 而不是
   原始变体 "葱段" / "葱丝"). 两端用同 lib (`dishIngredients.ts`) 保口径.
4. **toggle 双写**: setState (UI 即时) → LS persist (重启 fast read) → DB
   upsert (异步, 失败 console.warn 不抛错). 失败仍有 LS 兜底, 用户再点"通知
   菲佣"按钮可批量 commit 重试.
5. **兼容老数据**: DB 空但 LS 有 → mount 时一次性迁移上去, 写
   `nutri_inventory_migrated_<hid>_<date>` sentinel 防重跑.
6. **swapDish / 任何菜单改动**必须同时:
   - DB upsert (含 algo_version + cache_key)
   - LS `generatedMenu` 镜像 (今日)
   - dispatch `nutri-weekly-menu-changed` event 通知其它 hook 实例重读
