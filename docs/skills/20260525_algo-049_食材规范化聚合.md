# Skill · TICKET-049 食材规范化聚合（葱段+葱丝→葱）

日期: 2026-05-25
模块: 食材采购清单聚合
状态: shipped

## 三段大白话

### 1. 这事儿为什么要做

老板真测发现 `/verify-ingredients` 采购清单出现明显违和的两行：
"葱段 50g" 和 "葱丝 30g" —— 实际上买葱的时候没人分段还是丝，就是一根葱；
"猪前腿 200g" 和 "猪后腿 100g" 一样的情况 —— 走进肉档说"猪肉 300g"
而不是分开报部位。问题出在 `dishIngredients.aggregateIngredients` 用 `nameZh`
原始字串做聚合 key，prep_steps_json 里写啥就出啥，菜品 A 写"葱段"菜品 B
写"葱丝"就被当成两种东西分开列。结果就是清单又长又不科学，老板拒收。

### 2. 怎么修的

CEO 拍板**方案 1 静态字典**（也是最便宜的路径，零运行时成本、零 LLM 调用）：

- 新建 `src/lib/ingredientNormalization.ts`，里面有 `INGREDIENT_NORMALIZATION_MAP`
  字典 78 条，原始变体名 → canonical 名（葱段/葱丝/葱花→葱；猪前腿/猪后腿/五花肉→
  猪肉；蒜末/蒜片/蒜蓉→蒜；姜片/姜末/姜丝→姜；以及黄瓜/番茄/土豆/胡萝卜/青椒/
  辣椒的各种切法）。
- `normalizeIngredientName(rawName)` 三步匹配：精确命中 → 包含匹配
  (e.g. "猪肉 200g" → "猪肉") → fallback 原名。
- 改 `src/lib/dishIngredients.ts` 的 `aggregateIngredients`：聚合 key 从
  `ing.nameZh` 改成 `normalizeIngredientName(ing.nameZh)`，canonical 名直接覆盖
  `AggregatedIngredient.nameZh`，原始变体名收集到新加的 `variants[]` 字段。
- 改 `src/pages/VerifyIngredients.tsx`：category view + trip view 都在 canonical
  名下方加小字 `(葱段 + 葱丝)`，只有 `variants.length >= 2` 时显示（单一变体 =
  没合并 = 无信息量）。
- 同时在 `ingredientNormalization.ts` 留一份纯函数版 `aggregateIngredients`
  （签名跟 CEO spec 一致：`{name, quantity, unit?, sourceDishTitle?}`），给 node
  脚本 / 真测 / 未来其他入口用。两条聚合路径互不污染。

**保留原则**：
- 不同动物绝不合并（猪 ≠ 牛 ≠ 鸡 ≠ 鱼）
- 排骨保留（骨头+肉跟纯肉不同）
- 不同鱼种保留（鲈鱼/鲫鱼/鲷鱼 是不同鱼）
- 鸡部位保留（鸡胸 ≠ 鸡腿 ≠ 全鸡），但去切法（鸡胸肉→鸡胸）

### 3. 下次什么时候会再用到

- **任何"聚合两个看似不同实际同一物"的场景**：电商 SKU 去重、用户标签合并、
  地址归一化 …… 静态字典 + 精确-包含-fallback 三段匹配是低成本可控方案。
  比 LLM 归一化便宜 100×，比 Levenshtein 距离/嵌入向量更可解释。
- **采购清单 / 备菜 / 库存** 类清单聚合，扩字典即可加新合并规则。新增食材
  类别（e.g. "葱白/葱叶/小香葱根"）只需往 `INGREDIENT_NORMALIZATION_MAP`
  加几行，不动核心逻辑。
- **小心边界**：CEO 明确不合并的项目（排骨、不同鱼种、鸡部位）一定要在
  字典里 explicit 排除掉 + 文档里写清楚，否则后续维护者扩字典时容易踩坑。
  这个 ticket 把保留分类规则写在了 ingredientNormalization.ts 头部注释里。
- **真测要做**：上线前用 node 脚本跑 CEO spec mock 数据看输出符合预期
  （葱 80g / 猪肉 300g / 蒜 30g），别只看 TypeScript 编译过。
