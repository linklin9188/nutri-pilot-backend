# 微信公众号 IP 白名单漂移 — Railway 多 IP + JSSDK 诊断 (2026-05-26)

## 1. 问题

老板上午配好微信 JSSDK 分享卡片，下午用户反馈"微信登不上"。前端 console 报：
```
{"errcode":40164,"errmsg":"invalid ip 52.8.80.216, not in whitelist hint: [xxx]"}
```

但老板坚持"早上明明 ok 的"。真因：**Railway 部署 IP 会漂移**——服务每次重启 / scale /
冷启动，外网出口 IP 可能换。微信公众号侧 IP 白名单是**精确匹配**，
一漂就 40164。

而且不止一个 IP——上午配的 `162.220.232.6`，下午就成了 `52.8.80.216`。
Railway 这种 PaaS 的出口 IP 池可能有几十个，靠"加一个测一个"永远追不上。

## 2. 方法

**短期止血**：

1. 让老板把**最近 7 天报错日志里出现过的所有 IP**一次性全加微信白名单
   （公众号后台 → 开发 → 基本配置 → IP 白名单）。
2. 加完后 5-10 分钟微信侧缓存才完全更新，期间继续 40164 是正常的。
3. 后台 polling 验证脚本：
   ```bash
   while true; do
     curl -s "https://nothinkeats.com/api/wechat-jssdk-signature?url=https://nothinkeats.com/" \
       | jq -r '.errcode // "ok"'
     sleep 30
   done
   ```
   返 "ok" 表示当前出口 IP 已在白名单。

**中期方案**（CEO 待派）：

- 选 A：上 Railway **静态出口 IP add-on**（付费 $5/月，IP 永久固定，一劳永逸）
- 选 B：用 Cloudflare Workers 做微信 API 代理，固定 Workers 出口 IP（免费但要写代码）
- 选 C：迁 wechat-mp-callback 到 Supabase Edge Function（Frankfurt 出口 IP 相对稳定，已知 IP 池较小）

**JSSDK 诊断三连**（每次报错先跑）：

1. 看 Railway server 日志，grep `wechat-jssdk-signature` 拿真实出错 IP
2. 看微信报错的 `errmsg` 字段——`invalid ip X.X.X.X` 直接抄 X.X.X.X 加白名单
3. 加完不要立刻 retry，等 5 分钟微信侧 cache 过期，再 verify

**与 OAuth 登录的关系**：
- 微信 OAuth (wx_code → access_token) 也走同一个白名单，IP 漂移会同时挂登录 + JSSDK。
- 用户反馈"登不上"≠ OAuth 接口挂，可能是前端 redirect URL 配错——先 grep server 日志
  确认到底是 OAuth 报 40164 还是 JSSDK 报 40164，对症加 IP。

## 3. 标准

**今后所有需要"出口 IP 白名单"的第三方集成的不变量**：

1. **不要假设 IP 不变**：PaaS（Railway / Vercel / Render）出口 IP 都是池化的，部署即漂。
2. **白名单一次性加多 IP**：监控 7 天报错日志，把所有出现过的 IP 全加，不要"出一个加一个"。
3. **配后等缓存**：微信侧白名单 5-10 分钟才生效，立刻 retry 看不到效果不代表配错。
4. **静态出口 IP add-on > 追 IP**：$5/月省下每周一次"白名单漂移修复" 30 分钟工程时间。
5. **用户报"登不上"先看 Railway 日志**：grep 真实 errcode + IP，不要凭描述瞎猜。
6. **关键 secret 不进白名单逻辑**：白名单是网络层防护，不能替代 APPSECRET 校验。
