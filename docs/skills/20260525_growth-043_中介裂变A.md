# Skill: TICKET-043 中介裂变 A 推荐码 (PDPO 合规版)

老板拍板 2026-05-24 ship 中介裂变 ACD 三轴。A = 推荐码 attribution，低风险，符合香港 PDPO 个人资料隐私。

## 1. 一句话：这是干嘛的

给中介一个 6-8 位推荐码（e.g. `JJL2026`），用户注册时填一栏「中介推荐码（选填）」，后端把 `user_profiles.referred_by_agency_id` 写进去做 attribution。中介看不到客户名字电话，只内部统计「这个码带来了几个用户」，未来按头发超市券（5 HKD/人）—— 但发券是老板手动操作，本轮 schema 留位置不自动跑。

## 2. PDPO 合规边界（为什么不能做"你的中介是 X"提示）

香港 PDPO 第 6 原则：未经数据当事人同意不得披露其个人资料。如果 UI 显示「检测到推荐码 ABC，你的中介是 XX 公司」，等于把"用户和中介的关系"实时披露给用户 —— 用户对此可能没有明确同意（中介可能群发推荐码，用户不一定真认识中介）。所以：

- 推荐码 input 框：**不显回显**「检测到中介 X」
- 中介后台只看「我的推荐码带来 N 个用户 / 总奖励 HKD M」**聚合数字**，不下发用户名单
- 用户填错码 / 假码：**容错** —— 仍写 `referred_by_code` 留 record（不报错不阻塞登录），`referred_by_agency_id` 留 null

## 3. 实现要点（下次类似 ticket 复用）

- **新表 `agencies`**：referral_code unique + status (pending/active/paused) + reward_voucher_per_user。RLS `FOR SELECT USING (status = 'active')` 让前端可 query 验证码合法，但 pending 中介筛掉。
- **`user_profiles` 加两列**：`referred_by_agency_id uuid FK` + `referred_by_code text` 原文。两列都 nullable（CLAUDE.md 硬约束：新列全 nullable）。
- **3 个登录入口都要 attribute**：employer 微信 dev fallback / helper invite-code / learner signup。真 WeChat OAuth 路径需 edge fn 配套（落 userId 后 /auth/wechat/done 消费 `nutri_pending_ref_code` localStorage），本轮 ship TODO 注释留位。
- **`?ref=AIEATS_DEMO` URL 预填**：中介可分享 `https://nothinkeats.com/login?ref=XXX` 一键预填，复用 ?invite=ABC 的模式。
- **attribute 时机**：必须在 user_profiles upsert 之后跑 UPDATE，否则找不到 row。
