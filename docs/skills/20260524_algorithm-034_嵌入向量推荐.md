## 1. 解决了什么

算法从"硬分类字段打分"升级到"软向量相似度"——之前 axis 32-40 的 9 个偏好维度都
是 enum 字段对比 (`pmc='red'` vs `dish.protein_main_class='red'` 命中即 +0.30)，
冷启动用户填的字段稀疏 + 量级互压 + axis 互相抵消，导致推荐效果不稳定（v51-v54
反复 sim 调试 axis 32 量级 0.15→0.30 仍只把命中率从 20% 推到 30%）。

新范式 (Spotify / Netflix 同款)：用户通过 **图片选菜** 表达喜好 → 算法把代表菜
的 20 维 feature_vector 加权平均得到 user vector → 推荐时用余弦相似度找最像的菜
→ 在 top 100 内按营养目标重排 → 过敏硬过滤。

老板拍板"manual 20 维 不用 Gemini embedding + pgvector"——现阶段用户量小，
manual 已足够；pgvector 是未来主义，等数据飞轮跑起来再升级。manual 工程量
1-2 小时 vs pgvector 1-2 天。

## 2. 用了什么关键方法

### a) 20 维 manual feature vector (`src/lib/recommendVector.ts`)
- **cuisine 5 维 one-hot** [0..4]：chinese / western / japanese_korean / mixed /
  fusion (20+ 种 DB cuisine string 全 mapping，未识别落 mixed)
- **spice 1 维 [5]**：0-1 归一化 (number/5 或 mild/medium/heavy → 0.3/0.6/1.0)。
  dishes 表没 spice_level 列，预计算时从 `flavor_tags` 推断 (含 spicy → 0.8)
- **main_ingredient family 8 维 [6..13]**：red_meat / white_meat / seafood /
  vegetable / tofu / egg / carb / mixed
- **cooking_method 6 维 [14..19]**：steam / stir_fry / braise / boil / grill /
  deep_fry (DB cook_method 优先，缺失则 title 关键词 fallback 清蒸/炒/红烧...)

### b) Fallback cascade
新算法接入点在 `useWeeklyMenu.ts:3818` (`generateWeekPlan` 调用前)：
- 有 `user_profiles.preference_vector` → `recommendDishesByVector` 重排 pool top 150
  (远大于 5 slot×5 day = 25, 保留 generateWeekPlan 内 dedup/营养/per-member 多样性空间)
- 无 → finalPool=pool, 走原 scoreDish/scoreForWeek 路径不动 (旧用户零影响)

### c) 营养重排不污染向量空间
`nutritionRerankScore(dish, dietaryGoal)` 在 cosine top 100 之后才介入：
- fat_loss: 高蛋白 / 低脂 / 低 kcal +
- muscle_gain: 高蛋白 ++
- child_growth: 高钙 + 低盐 + 适量蛋白
- elder_wellness: 低盐 + 低油 ++
- general: 不调整

营养 reranking 只在 cosine 排好的 100 内重洗，保证"在你喜欢的范围内挑健康的"
而不是"为了健康推你不爱吃的"。

### d) 预计算脚本 (`scripts/compute-dish-feature-vector.ts`)
pg 直连 DB, 批量 100 行/批, 924/924 全填充, 用时 224.6s。idempotent（默认
`feature_vector IS NULL` 跳已填行）。

### e) 真测验证
模拟用户选 [鱼香肉丝, 麻婆豆腐] 4 道辣菜 → top 10 推荐 100% 中餐 100% 辣菜
(干煸牛肉丝/回锅肉/农家小炒肉/尖椒肉片/孜然羊肉/川味牛肉/杭椒牛柳/鱼香肉丝)。

## 3. 下次同类任务标准

1. **任何"软偏好"特性优先用向量不用枚举字段**。axis 加来加去互相抵消是设计气味；
   向量+cosine 一次到位。
2. **新算法必有 fallback 兼容旧数据**。preference_vector 缺失走旧路径，不是"未填
   等于全零向量"——后者会让所有旧用户突然拿到陌生推荐。
3. **ALGO_VERSION 必 bump**，注释里写清楚"什么变了 + 为什么 bump"。这次 v64→v65。
4. **预计算脚本必跑一次确认 dish 数据完整**。脚本输出填充率统计 (100.0%)，下游
   就不需要 forward-compat 兜底 vector 缺失的情况了。
5. **schema 列必先实查再写脚本**。第一版脚本 SELECT spice_level 直接报错——
   dishes 没这列，flavor_tags 才是真值；CLAUDE.md "remote DB 是 truth" 再提醒一次。
6. **DISH_FIELDS append 而不是替换**。新加 feature_vector 列只 `DISH_FIELDS + ',feature_vector'`，
   不动 dishFields.ts 主常量，避免影响其他 reader (VerifyIngredients 等)。
7. **数据库 numeric[] 回前端可能是 string array**。Postgres jsbi/decimal 用
   string 序列化，必须 `parseFloat(String(x))` 兜底，否则 cosine 算出 NaN。
