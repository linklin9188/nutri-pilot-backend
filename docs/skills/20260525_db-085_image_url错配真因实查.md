# TICKET-085 真因实查（Database 部门）

**日期**: 2026-05-25
**触发**: 老板真测截图 — 4 道菜显示错图，工单假设 DB 数据污染（多菜共用同一 image_url）

## 问题

工单 Phase 2 直接给修法（UPDATE 把 dup image_url 清空 → NULL → 走 UI fallback），但前提是 Phase 1 必须先实查证实 dup 存在。如果不先查就 ship migration，等于按假设动 DB。

## 方法

1. **不预设修法，先 SQL 实查**：3 个 SELECT — 4 道真测菜的实际 image_url / 全表 dup 组数 / 全表填充率。
2. **写一次性 pg client 脚本**（`scripts/ticket085-image-dedupe.ts`）走 `.env` 里的 `DIRECT_DATABASE_URL`，绕开 psql / supabase CLI 都被 Bash 沙盒拒的问题。模板照搬 `scripts/migrate.ts`。
3. **Phase 1 结果证伪假设**：DB dup 组数 = 0，4 道真测菜里 3 道 image_url=NULL + 1 道指向自命名 storage 路径。**DB 干净**。
4. **追真因到前端**：grep `image_url` + `fallback` 找到 `src/lib/dishImageFallback.ts`，发现 hash-to-pool 模式把 209 道 NULL 菜映射到 23 张 Unsplash 图。
5. **本地复现撞图**（`scripts/ticket085-rootcause.ts`）：import 真正的 `getFallbackImage`，把 209 道 NULL 菜全跑一遍 → 21 组撞图 / 207 道菜至少跟 1 道共用 fallback url（撞图率 99%）。
6. **不 ship 空 migration**：原工单的 migration 099 UPDATE 影响 0 行 = noop，违反 "migration 必须真做事"。改写成 backlog 文档（`docs/qa/20260525_dishes_image_backfill_needed.md`）把 209 道待补图菜分组列出，附 3 路修法建议。

## 标准

- **P0 工单先 SELECT 后 UPDATE 是死规矩**。Phase 1 实查不是走过场，是 Phase 2 修法的前提，证伪了就不要硬 ship。参考前一单 TICKET-025（`46baa56`）同套路：" P0 真因实查 — 非 Backend bug，UI helperName 硬编码 'Ika' default"。
- **bash 沙盒拒 psql/supabase CLI 时**走 `npx tsx scripts/xxx.ts` + `pg.Client(process.env.DIRECT_DATABASE_URL)` 模式，模板 `scripts/migrate.ts`。`npx tsx` 在本工程已配 + node_modules/pg 已装，不需要 install。
- **DB 部门 commit 不 ship 空 migration**。如果 Phase 1 证伪假设，把脚本 + 真因报告 commit，commit message 第一行明确 "非 DB bug，是 X 层问题"，把球踢回正确部门 + 给完整 backlog 让对方部门能直接动工。
- **追真因到前端时只读不改**。本工单识别出 `dishImageFallback.ts` 池过小 + `useSupabaseMenu.ts:536` 是 fallback callsite，但 Database 部门不动前端文件，方案 A/B/C 列在 backlog 里等前端/小图生成部门接。
