**日期**: 2026-05-25

**触发**: 老板真测 #3 — Settings 加家庭成员后菜单完全没变化
**长期方案**: 走 PENDING_BOSS_DECISION (family_members DB schema 升级 + 算法 cascade vector 读家人)

## 大白话三段

### 1. 为什么"加家人菜单不变"是 bug

老板在 Settings 加了第 2 个家庭成员。期望: 菜单分量 / 道数 / 多样性立即变化反映新家庭。实测: 菜单纹丝不动。

3 个隐藏原因:

- **cache 命中**: useWeeklyMenu 走 localStorage + DB 双层缓存，按 `(ALGO_VERSION, weekStart, dishesPerDay, cuisine, eating, intent, cook, byDay)` 算 cache_key。加家人后只动了 `nutri_family_members`，但 cache_key 完全没包含这个字段，所以旧 cache 仍 hit，菜单不重生。
- **dishesPerDay 桶化**: 即使 calcDishCount 间接读 eating members，1人→2人时 dishesPerDay 可能从 2→3 (eff=adults+kids×0.5 round)，但若 eating_today 没勾新家人，eating 数仍 1, dishesPerDay 不变。
- **event 链断**: Settings persistMembers 只 dispatch `nutri-prefs-changed`，对 family 场景语义不清晰; useWeeklyMenu 虽然监听了 prefs-changed，但 cache_key 不含家人维度，clear 后重算也得到同一 key 同一菜单 (DB cache 仍 hit)。

### 2. 短期 hack 3 件套 (CEO 自决, 不动 DB schema)

- **(1) cache_key 加 `_h{homeMembersCount}` suffix** — `useWeeklyMenu.ts:856-862`。直接读 `nutri_family_members` JSON 算 length 拼到 cache_key 末尾。加家人 → length 变 → cache_key 变 → localStorage cache miss + DB cache (loadFromDB 对比 cache_key 列) 也 miss → 必走 generateWeekPlan 重算。
- **(2) calcDishesForToday 出口 floor 兜底** — `useWeeklyMenu.ts:788-799`。计算完 dishesPerDay 后, `total = max(total, min(9, homeMembers.length))`。保证"家里 3 口就至少 3 道菜", 不管 nutri_eating_today 勾了几个。也让用户感知菜数差异(老板真测最直观)。
- **(3) Settings persistMembers 加 dispatch + useWeeklyMenu 加监听** — `Settings.tsx:324` + `useWeeklyMenu.ts:3544-3550`。显式 `nutri-home-changed` event 通道, 与 nutri-prefs-changed 同 handler (clear cache + setRefreshKey). 语义独立, 便于未来接长期方案单独触发。

### 3. 长期方案 (PENDING_BOSS_DECISION)

短期 hack 只让"加家人 → 菜单道数变"，算法本身**仍未真正用家人数据**(年龄/性别/目标/过敏)做评分。

长期需要:
- DB 加 `family_members` 表 (id, user_id, name, birth_year, gender, dietary_goal, allergens, life_stage)
- `user_profiles.preference_vector` 嵌入向量改为 family-aware (家人 goals/allergens union)
- `useWeeklyMenu` cascade vector path 显式读家人, scoreForWeek 加 family-fit 维度
- Settings UI 把家人 CRUD 写 DB 而非 localStorage

老板未拍板 schema 升级时机，本 ticket 不动。

## scale 注释 — 不要扩散这个 hack

**Do NOT**:
- 把 `nutri_family_members` JSON parse 散播到更多文件 — 已经在 4 处 (Settings persist + useWeeklyMenu 两处计算 + familyPrefs.ts loadAllMembers)。长期方案接 DB 表后这 4 处都要回收。
- 把 home-size floor 抄到 `useSupabaseMenu.calcDishCount` — calcDishCount 是 cuisine-aware 桶化算法的 canonical source, 加 home-size 兜底会破坏 western/中餐分支语义。floor 只放 useWeeklyMenu.calcDishesForToday wrapper 出口。
- 给 `nutri-home-changed` event 加重 payload — 当前是 empty Event, 与 nutri-prefs-changed 一样无状态. 加 payload 后 useWeeklyMenu handler 需要类型导航, scale 性差。

**Do**:
- 接长期方案时, 第一步先把 `loadAllMembers()` (familyPrefs.ts) 改成 DB-first, localStorage fallback; useWeeklyMenu + Settings 共享同一 source of truth, 这 3 件套 hack 自然 simplify。
- 若加新触发场景 (e.g. helper 加家人代填), dispatch `nutri-home-changed` 即可, 不要再造第 4 个 event。

## 真测说明 (待 CEO 验证)

1. **场景 A**: Settings 加 1 个家庭成员 (普通成人) → 返回 Home/WeeklyMenu。
   - 预期: 菜单立刻 loading → 重生, 道数 ≥ 2 (从原 1 人 2 道 floor 到 ≥ 2)。
   - 验证点: F12 console 看 `weekly_menu_v67_..._h2` 这种 key 出现 (而非 `_h1`)。
2. **场景 B**: 删除一个家庭成员 → 同上观察 → key 应回到 `_h{N-1}`, 菜单重生。
3. **场景 C**: 同一周内 calc dishesPerDay 不变 (例: 已经 5 道菜, 加第 6 个家人) → cache_key 仍因 `_h6` 段变化 invalidate, 菜单重生 (虽然 dishesPerDay 还是 cap 9 或不变)。
